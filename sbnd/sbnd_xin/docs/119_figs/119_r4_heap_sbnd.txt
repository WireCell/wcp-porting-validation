THE STAGE, AND WHY THE WITHIN-STAGE SPLIT IS NOT A TARGET
---------------------------------------------------------------------------------------
Peak dumps are SPIKES above an oscillating plateau, not a single plateau: SBND evt11239 runs
~600 MB, spikes to 932 at i6, and settles to ~350 MB from i17 on; PDVD runs ~1950 MB, spikes to
2750 at i32, settles to ~1220.  Each oscillation is one cluster's retile-graph-Steiner cycle.
So the DUMP POSITION selects a phase, and the sub-attribution follows the phase -- within ONE
SBND event:

  dump            CreateSteinerGraph::visit   connect_graph_closely_pid   create_steiner_tree
  SBND i6  (932 MB)        78.0 %                     59.2 %                    absent
  SBND i16 (687 MB)        69.9 %                      2.6 %                    24.2 %
  SBND i32 (373 MB)        18.6 %                      1.4 %                     0.1 %
  PDVD i6  (976 MB)        19.7 %                      0.4 %                     0.2 %
  PDVD i32 (2750 MB)       71.6 %                      2.1 %                    29.4 %

The split between connect_graph_closely_pid and create_steiner_tree SWAPS between two dumps of
the same event on the same detector.  They are two phases of one stage, NOT two detector-specific
targets, and this instrument cannot separate them.  Any claim that one of them is "the" site is
an artefact of which dump was read.

WHAT IS STABLE ACROSS BOTH DETECTORS AND EVERY PHASE
---------------------------------------------------------------------------------------
  1. CreateSteinerGraph::visit is the stage: 78.0 / 69.9 % (SBND, two peaks) and 71.6 % (PDVD)
     of peak live heap.
  2. ImproveCluster_2::mutate -- the RETILE SAMPLER (CreateSteinerGraph.cxx:322,
     m_grapher_config.retile->mutate) -- is 17.0 / 14.4 % (SBND) and 20.7 / 17.7 % (PDVD),
     i.e. present and sizeable in EVERY phase including ones where the stage itself is small.
     The FRACTION is what is stable; the absolute is not, and must not be read as a fixed block
     that could be deleted.  On SBND evt11239 it is 158.5 MB at i6, 98.9 at i16, 61.7 at i32 --
     a 2.5x range while the share holds.  It SCALES WITH THE CLUSTER.  That is the right shape
     for a lever (shrink the retile output and the graph built on it shrinks with it) but it is
     not a removable fifth of the peak.

  (2) is the round's result.  Doc 119 round 0 named the retile sampler as the #1 CPU target on
  all three detectors (53-60 % of Steiner's time).  It is now also a stable sixth-to-fifth of
  peak live heap on two detectors.  The CPU target and the memory target are the SAME OBJECT.

TWO READINGS THIS ROUND RETRACTED, AND THE RULE THEY GIVE
---------------------------------------------------------------------------------------
Both came from google-pprof frames marked "(inline)", and both were refuted by primary evidence
within minutes of being formed.  Neither reached a conclusion; they are recorded so the next
round does not re-derive them.

  a) "boost::vec_adj_list_impl::copy_impl at 1254 MB (45.6 % of PDVD's peak) is the graph COPY in
     Steiner::reweight_base_graph (doc pdvd/115 pricing, SteinerBaseWeight.h:84 `Graph out =
     base;`), so the doc-118 base_weight flip is the memory tail."
     REFUTED by the job's own log: 409 pricing calls in this event, the largest 62 vertices /
     450 edges.  All the priced graphs together are a few MB.  The copy is real code and it is
     not this memory.

  b) "add_edge allocating _Rb_tree nodes (809 MB) and list nodes (632 MB) means the Steiner graph
     stores one red-black-tree node per edge, so the edge container is the target."
     REFUTED by the typedef: Graphs.h:23 is boost::adjacency_list<vecS, vecS, undirectedS, ...>.
     Both vertex and edge storage are vectors.  There is no per-edge tree or list node in this
     graph at all; those containers belong to something else that pprof folded into the same
     inline chain.

  RULE: in this profile, trust NAMED NON-INLINE frames (CreateSteinerGraph::visit,
  ImproveCluster_2::mutate, connect_graph_closely_pid).  Treat every "(inline)" frame and every
  std:: / boost:: container frame as unattributed -- the inline chain is reconstructed, not
  observed, and it was wrong twice here in one profile.  Going deeper needs a different
  instrument (a frame-pointer build), not a closer reading of this one.

AN INCIDENTAL FLOOR
---------------------------------------------------------------------------------------
UbooneNueBDTScorer::ensure_readers -> TMVA::MethodBase::ReadStateFromFile holds 145.0 MB that is
still live at exit (45.7 % of the median event's final live heap).  It is allocated once under
call_once and never released.  Not a tail contributor -- it is the same 145 MB on every event --
but it is a floor under every SBND PR job and it is the largest single thing alive at exit.
