MLDataWriters — plan

One modular family of writers for nugraph, DL-vertexing and BDT training data, built on the MABC visitor pattern: no extra serialization, and TensorSetLabeler stops growing.

Work dir /exp/sbnd/data/users/yuhw/production-prep/mldatawriters-dev · ai-helper #15 · not related to the CAF project (#14) · 2026-08-20

Short answer: yes, the MABC + visitor pattern is the right shape, and there is already a working in-tree precedent — three MABC visitors write their own output files today (SbndPrMagnifyTrackingVisitor and UbooneTaggerOutputVisitor write ROOT, PrDisplayDump writes JSON), and the toolkit ships HDF5 via hio (HDF, HioTensorSink).

But one hard constraint shapes everything: a WCT visitor cannot reach art::Event, and all three writers need truth. So the design is one art-side truth injector plus N pure-WCT writers — which is also exactly what stops TensorSetLabeler growing.

1. Why this needs restructuring

TensorSetLabeler is 1731 lines of .cxx and 370 of header doing four separable jobs: truth association, the truth_per_track tensor, several families of Bee sets, and the nugraph HDF5. Two more writers (DL-vertexing, BDT) would push it past any reasonable size, and its Bee half already needed splitting once — the bee_sets / label_blobs knobs added for the two-instance PR-chain work.

The other pressure is serialization. Each art-level module in the chain deserializes the point-cloud tree, mutates it, and re-serializes: as_pctree → work → as_tensors. Chaining writers as separate ITensorSetFilters multiplies that round trip for no benefit, since they all want the same tree.

2. The constraint that decides the architecture

Each writer's inputs, and where those inputs actually live. Measured, not assumed — the PC list is read off a real serialized tree and the runtime objects off the source.

WriterNeedsSurvives serialization?Can be a visitor?
nugraph 3d blob points, the six 2-D ctpc_a{0,1}f0p{U,V,W} PCs, per-blob truth trackid, nu truth yes, all of it yes — or downstream, either works
DL-vertexing 3d (x, y, z, q) + the true neutrino vertex yes — 3d is a PC; nu_vtx_* is in the tensor-set metadata yes
BDT TaggerInfo, KineInfo, the PR graph / TrackFitting NO visitor ONLY
The asymmetry is the whole design. as_tensors serializes only node->value.local_pcs() (aux/src/TensorDMpointtree.cxx:82), while TrackFitting is a private facade member — std::shared_ptr<TrackFitting> m_track_fitting (Facade_Grouping.h:392), with a named-slot map at :393. It is not a point cloud, so it is never written and dies when MABC::operator() returns.

So BDT training data can only be produced from inside the MABC pipeline — there is no downstream position from which it is even visible. That single fact settles the question: the visitor pattern is not merely convenient here, it is required for one of the three writers, and adopting it for all three makes them uniform.

For the record, the full set of PCs that do survive: 3d, scalar, cluster_scalar, grouping_scalar, perblob, steiner_pc, corner, ctpc_a{0,1}f0p{U,V,W}, dead_winds_*, dead_gap_*, flash, flashlight, opflash, light.

3. The art boundary, and the one channel across it

Truth comes from art::Event — MCTruth, MCParticle, SimEnergyDeposit. A WCT visitor gets visit(Facade::Ensemble&) and nothing else: no art event, no ITensorSet, not even an ident. So truth must be injected into the tree by an art-aware component before any visitor can use it.

Two injection channels already exist and are proven:

ChannelCarriesProven by
blob-level scalar PCper-blob truth trackid the labeler writes it; verified to survive switch_scope, unmerge_bundle, unmerge_assoc and protect_bundle (issue #13) because it rides the blob node, while switch_scope erases only the cluster-level perblob
ensemble scalar PCevent-level values, e.g. RSE and the true nu vertex MABC already stamps ensemble.set_scalar<int>("runNo", …) so the ROOT visitors can identify their event (issue #13 §7.3). The same channel carries nu_vtx_{x,y,z}.

Note the gap this closes. The nu truth currently lives in the tensor-set metadata (n_nu, nu_pdg, nu_energy, nu_vtx_{x,y,z}, nu_ccnc, nu_int_type, nu_flavor, nu_edep). Visitors cannot see set metadata — only the Ensemble. So a DL-vertexing visitor needs the vertex re-published as an ensemble scalar. That is a few lines in the injector, using a mechanism that already exists.

4. Proposed shape

art  ┌─────────────────────────────────────────────────────────────┐
     │ larwirecell:  TruthInjector        (the ONLY art touchpoint) │
     │   reads MCTruth / MCParticle / SimEnergyDeposit once         │
     │   writes  blob scalar.trackid  +  truth_per_track tensor     │
     │   publishes nu truth as ensemble scalars                     │
     └─────────────────────────────────────────────────────────────┘
                                 │  one tree, no extra round trip
WCT  ┌──────────────────────────┴──────────────────────────────────┐
     │ MABC pipeline (visitors, in declaration order)               │
     │   … clustering / tagger stages …                             │
     │   NuGraphWriter      3d + ctpc_* + trackid   -> HDF5         │
     │   DLVertexWriter     3d + nu_vtx             -> HDF5         │
     │   BDTDataWriter      TaggerInfo / KineInfo   -> ROOT or HDF5 │
     └─────────────────────────────────────────────────────────────┘

What this buys

  • No extra serialization. Visitors read the live tree. The only as_pctree/as_tensors pair is the one the chain already pays.
  • One art touchpoint. Truth is ingested once, not once per writer.
  • TensorSetLabeler shrinks. It becomes the injector; nugraph and the Bee sets move out. Each writer is independently readable and testable.
  • Uniform placement. A writer is enabled by adding its name to pipeline_names — the same switch that controls every other stage.
  • BDT becomes possible at all, which it is not downstream.

What it costs

  • Writers live in WCT, so they cannot ever touch art — anything new they need from truth must go through the injector.
  • Placement is no longer free: a writer must be named in the pipeline of the right MABC (see §5), which is a real ordering constraint rather than a wiring detail.
  • Moving nugraph out of TensorSetLabeler must be proven byte-identical, or it is a silent physics change to training data.

5. Pitfalls to design out from the start

Fixed output filenames break multi-event runs. This is not hypothetical: tracking-pr.root is written by two visitors sharing one filename, one opening RECREATE and the other UPDATE, so lar -n N silently yields an 8 kB file with T_tagger and T_kine absent (issue #13 G9). A new writer family must handle many events per process by construction — append per event, or take the filename per event — and must never leave a truncated file looking like a legitimate one.
"No content" must be distinguishable from "failed". On the run-925-23 sample, 6 of 10 events had no neutrino candidate, and their tracking-pr.root is byte-indistinguishable from the corrupted multi-event case. A writer should record an explicit empty record rather than omit the event, so a downstream trainer can tell the two apart.
Silent fallbacks. The recurring failure mode in this chain is plausible output computed the wrong way — the sp.jsonnet extVar that silently selected the wrong ROI thresholds, the DL vertex that silently falls back to geometric without torch. Each writer should assert its inputs are present and say so loudly when they are not, and sbnd/check-pr-run.sh should gain a check per writer.

6. Phasing

  1. Split, do not add. Move nugraph out of TensorSetLabeler into NuGraphWriter with no behaviour change, and gate it byte-identically against the current nugraph.h5. This proves the pattern on something whose right answer is already known.
  2. DLVertexWriter — the smallest new writer: 3d + the nu vertex re-published as an ensemble scalar.
  3. BDTDataWriter — the one that needs the visitor position. Start from what UbooneTaggerOutputVisitor already reads (tf->get_tagger_info(), get_kine_info()).
  4. Shared plumbing — factor the common HDF5/append/empty-record handling once the third writer shows what is actually common. Not before.

7. Open questions

  1. Is BDT here "write the existing 1216 features for retraining", or "write a new feature set"? The first is a dump of TaggerInfo and is nearly free; the second is a physics project. This changes the scope more than anything else on the page.
  2. One file per writer per job, or one shared HDF5? Shared is tidier for a trainer; separate is far simpler for multi-event append and for re-running one writer alone.
  3. Does the DL-vertexing training data need the fitted trajectory (T_rec_charge-equivalent), or only blob points? If the fit is wanted, it must first be persisted into PCs — TaggerCheckSTM's save_stm_fit shows how (cluster.local_pcs()["stm_fit"], .cxx:808), and TaggerCheckNeutrino has no equivalent yet.
  4. Do these writers run in production, or only in dedicated training-data jobs? Production-on means every knob is a physics commitment; training-only means they can move fast.
  5. Keep the name TensorSetLabeler for the slimmed injector, or rename to something like TruthInjector? Renaming is honest but breaks every existing fcl.
