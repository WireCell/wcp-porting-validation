6. Does the PR chain throw away out-of-beam-window clusters?

No. Nothing in the PR chain deletes a cluster or a blob on beam-window grounds. Three separate mechanisms narrow the population, they are easy to conflate, and only one of them touches an output file — and that one filters by active volume, not by time.

6.1 switch_scope — a volume split, and the only stage that restructures the tree

clustering_switch_scope.cxx corrects every blob's 3-D points, then calls live_grouping.separate(cluster, filter_results, true), splitting each cluster in two: id=1 = at least one corrected point lands inside the active detector volume, id=0 = none do. Both children stay in the grouping, distinguished only by a scope_filter boolean. Blob count is conserved; the per-blob provenance arrays (real_cluster_id, assoc_cluster_id, …) are row-partitioned to follow their blobs.

This has nothing to do with the beam window. An out-of-time cosmic sitting fully inside the TPC is id=1, in scope, and fully retained. What scope_filter=false marks are the geometrically out-of-volume shards — which is why the taggers use require_in_scope: on a 10-event sample those shards were 43% of all "mains" and tagged TGM at 85% vs 44% for real clusters.

The consequence to keep in mind is semantic, not lossy. An out-of-window cluster emerges from the PR stage un-evaluated, which is not the same as evaluated and found not to be a cosmic. Anything downstream reading flag_TGM/STM/FC must not read "no flag" as "not a cosmic". This is already how nusel_extract.py behaves — it emits not-tagged for out-of-window bundles and -1 for an absent FC verdict.

6.3 The splitters only ever add

unmerge_bundle, unmerge_assoc and protect_bundle all call grouping.separate(cluster, groups) with remove=false — the largest part stays put, fragments become new children. Each carries an explicit "BLOB LOSS in separate(): {} + {} != {}" error check on the sums. The only destroy_child() in the whole PR pipeline is in CreateSteinerGraph, and it destroys the temporary retiled copy that same function just created (CreateSteinerGraph.cxx:241,254,285) — never a source cluster.

6.4 Where things do disappear: the Bee display, by volume

MultiAlgBlobClustering's bee_points_sets entries take a filter that defaults to 1 (MultiAlgBlobClustering.cxx:253,1787): dump a cluster only if its scope_filter is true. 0 = dump everything, -1 = inverse.

So mabc-pr.zip's clustering layer holds exactly the in-scope set — which is precisely why nusel_extract.py reads that zip to recover the scope-filter state (it is runtime-only and never persisted). Out-of-beam-window cosmics are still in the Bee dump, as long as they are inside the active volume; what is dropped are the out-of-volume shards from §6.1.

Separately, the three PR-only Bee layers (track_fit, shower_track, vertices) set require_pr_graph: true, so on an event where the neutrino tagger selects no candidate those layers come out empty rather than falling back to dumping the whole clustering in raw coordinates (doc pr/3 §9).

6.5 The tensor output is unfiltered

as_tensors(*node, outpath(...)) at MultiAlgBlobClustering.cxx:2701 serializes the whole grouping node. No scope filter, no beam-window filter. So both the pctree tarball and the in-memory edge to the next graph node carry every cluster — in or out of window, in or out of scope. Nothing is lost for any downstream consumer.

Net answer for the 1-step. Adding the PR stages is additive with respect to content: no cosmic is discarded. But the PR node is not transparent with respect to structure — switch_scope, unmerge_bundle, unmerge_assoc and protect_bundle all split clusters, and the MABC's cluster_id_order: 'tree' renumbers idents 1..N after every step. See §6.6, which is the one thing I would not have predicted.

6.6 The consequence that actually matters: the labeler sits downstream

Our graph is clus_all_apa → pr_node → labeler → sink. The wclsTensorSetLabeler therefore attaches truth to the post-PR, already-split and already-renumbered clustering — not to the all-APA one that mabc.zip's clustering-global layer shows.

That is true today with 8 PR stages. Adding protect_bundle splits more clusters, so cluster idents seen by the labeler — and by its tagger_stm/tgm/fc Bee sets — will move. Anything that joins truth labels to Bee cluster IDs across the existing 13,217-event run would need regenerating, not just extending.

Two ways out, worth deciding before the pilot:

  • Move the labeler upstream of pr_node (clus_all_apa → labeler → pr_node), so truth is attached to the stable all-APA clustering and the PR stage becomes a pure consumer. Cleanest, and it makes truth labels independent of every PR knob.
  • Leave it downstream and accept that truth labels are PR-configuration-dependent. Defensible if the point is to study tagger performance on the PR clustering itself.

Note this is a pre-existing property of the 1-step, not something the PR extension introduces — the extension just makes it bite harder.

Only J3b needs the PR verdicts. The split is clean and follows the data.

Truth labels survive the PR splits automatically. J1 writes trackid into the blob node's "scalar" local PC, whereas switch_scope erases only the cluster-level "perblob" dataset. separate() moves blob nodes wholesale, so their node-local PCs travel with them through unmerge_bundle, unmerge_assoc and protect_bundle untouched. Putting the labeler before the PR node is therefore safe — no carry-list entry needed.

And it passes non-live tensors straight through (TensorSetLabeler.cxx:1656-1662): it re-serializes only pointtrees/N/live and copies every other tensor verbatim, so the dead grouping survives and fiducialutils downstream still gets what it needs. The labeler is safe to place mid-graph.

Three things break with two naive instances

  1. The tagger Bee set names are hardcoded (Bee::Points bpts_stm(m_bee_detector, "tagger_stm"), .cxx:1094-1100) — not derived from bee_algorithm. Both instances writing into the shared bee_sink would emit two data/N/N-tagger_stm.json entries into one zip. Instance A's copy would be all-zero verdicts, since the flags do not exist yet.
  2. Instance B would destroy instance A's labels. The trackid write-back at .cxx:1190-1196 is not gated on is_sim: int tid = -1;, then an empty projection loop, then an unconditional write. A second instance configured reality: "data" would stamp trackid = -1 over every blob A had labeled. Configuring it reality: "sim" avoids that but re-runs the full depo projection — paying the most expensive part of the labeler twice per event.
  3. nugraph.h5 collision — already solvable, hdf5_output and hdf5_filename are both per-instance config.

The minimal C++ addition

Everything else is already per-instance (inpath, grouping, reality, bee_sink, hdf5_output, hdf5_filename, beam_window, tagger_coords). Add two knobs, both defaulting to the current behaviour so every existing config stays byte-identical:

KnobDefaultEffect
label_blobstrue false skips the depo projection and the trackid write-back — fixes breakage 2 and makes instance B cheap
bee_sets["truth","sed","tagger"] selects which Bee families this instance emits — fixes breakage 1

Resulting configuration

clus_all_apa ── labeler_truth ── pr_node ── labeler_tagger ── TensorFileSink

  reality:      sim | data              reality:      sim | data

Both stay registered as fcl inputers under distinct names (wclsTensorSetLabeler:labeler_truth, ...:labeler_tagger), so each gets its own visit(art::Event&); B's returns early in data mode and is cheap in sim once label_blobs=false.

Bonus: this also opens the clean route for G3. The labeler already stamps the true RSE into its output tensor-set metadata (.cxx:1685-1687: set_md["runNo"/"subRunNo"/"eventNo"] = m_run/m_sub/m_evt). This supersedes option (d) there: cheaper, and it falls out of a reordering we want anyway.

7.1 G3 in detail — where SbndPrMagnifyTrackingVisitor is actually called

It is not a pgraph node. It is an IEnsembleVisitor living inside the clus_pr MABC's pipeline: list — the same slot every Clustering* module occupies. Full path:

fcl  wcls-img-clus-matching-xin.fcl        producer sig2img, plugin WireCellRoot loaded
 └─ jsonnet  clus.jsonnet cm_by_name.tracking_visitor
       { type: 'SbndPrMagnifyTrackingVisitor', name: 'pr',
         data: { runNo: runNo, subRunNo: subRunNo, eventNo: eventNo, ... } }   ← RSE frozen HERE
       cm_pipeline = [cm_by_name[n] for n in pipeline_names]
       clus_pr MABC   data.pipeline = wc.tns(cm_pipeline)
 └─ C++   MultiAlgBlobClustering::configure()          :224  for (auto jtn : cfg["pipeline"])
                                                       :227  Factory::find_tn<IEnsembleVisitor>(tn)
          MultiAlgBlobClustering::operator()           :2900 for (const auto& cmeth : m_pipeline)
                                                       :2901     cmeth.meth->visit(ensemble);

So the visitor is invoked once per event, in pipeline_names order, by the MABC that owns it. It never sees the ITensorSet, the frame, or the art event — the interface is virtual void visit(Facade::Ensemble&) const and that is the whole of it. An Ensemble is the point-cloud tree facade; it carries no ident and no RSE. That is the structural reason the visitor cannot identify its own event: there is nothing to ask.

Why rse_from_ident would only be a half-fix

MABC's own rse_from_ident reads the ident off the input tensor set and then does (MultiAlgBlobClustering.cxx:2813):

// The tensor ident already carries the real event id (raw, unmasked);
// run/subrun are not available in this chain.
m_runNo = 0; m_subRunNo = 0; m_eventNo = ident;

The ident traces back to CookedFrameSource.cxx:213, new Aux::SimpleFrame(event.event(), …) — the art event number and nothing else. Copying this mechanism into the ROOT visitors would give Trun = 0/0/<event>, not the true RSE.

Measured on the smoke-test event — and it exposes a pre-existing inconsistency

Every Bee layer in one mabc.zip, by writer:

The same zip carries two different run numbers. The event number agrees (3) only because ident happens to be the art event number. This is not introduced by the PR extension — it is the state of every zip our 13,217-event run produced. It has been harmless so far because the harness keys events by filename and by the RSE it greps from the log, never by the Bee metadata.

The real RSE is already inside the process

TensorSetLabeler is registered in the fcl as an inputer, i.e. an art-event visitor, and TensorSetLabeler.cxx:495-497 does exactly what WCT cannot:

void AIML::TensorSetLabeler::visit(art::Event& event)   // called at EVENT START,
{                                                       // before the pgraph runs
  m_run = event.run();  m_sub = event.subRun();  m_evt = event.event();

That hook fires before the graph executes, so the true run/subrun/event are known in-process before clus_pr — and therefore before tracking_visitor — ever runs. The information is present and merely has no route to the WCT side.

Options, re-ranked with that in mind

OptionCostGets correct run/subrun?
(a) Harness names outputs by RSE (it already greps it) and treats the filename as the keyzero coden/a — sidesteps rather than fixes
(b) Pass RSE through fcl params per lar call needs an RSE lookup pass first, since the harness addresses events by --nskip k yes
(c) rse_from_ident on the two ROOT visitorssmall C++ no — event only, run/subrun stay 0
(d) A wcls inputer that broadcasts the art RSE into the WCT components at event start (the labeler already proves the hook exists and fires early enough) small C++, new component yes — and it fixes the MABC/labeler mismatch above at the same time
(e) Route B — run the 2-step PR job, which takes RSE as per-event TLAs none, already supportedyes
Revised recommendation: (a) for the pilot, (e) as the reference arm, and (d) as the principled fix if the 1-step goes to production — not (c), which I proposed in the first draft before checking what ident actually carries. (d) is the only option that also repairs the two-run-numbers-in-one-zip problem.

What it uniquely provides: one row per qualifying bundle — every cluster that is both flag_main_cluster and in scope — labelled TGM / STM / LM / nu-candidate / not-tagged / no-bundle, with flashes de-duplicated across APAs. Nothing else we produce covers that population:

T_tagger1 entry per event — the single neutrino candidate the tagger selected~580 branches of detail on that one
tagger_{stm,tgm,fc,lm} Bee setsin-window main candidates verdict per candidate, but as a display, not a table
harness summary.csvevery event none — rc, wall time, zip size only
the run logevery evaluated main cluster N → TGM=… per cluster, plus "N main(s) evaluated, M out of window"

So if the question is "what fraction of bundles get TGM-tagged across 13k events", T_tagger genuinely cannot answer it. But the log already carries the per-cluster verdicts that nusel_extract.py itself parses — it needs the pctree only for bundle structure and mabc-pr.zip only to recover the runtime scope filter. A small tabulator over the logs plus the clustering-pr Bee layer would answer the same question without G6.

And it would now give a wrong answer on our output. nusel_extract.py selects the in-scope set with endswith('-clustering-global.json'). After the §7.4 merge our single zip contains both 0-clustering-global.json (all-APA, 9 clusters) and 0-clustering-pr-global.json (PR in-scope, 30). That grep matches the all-APA layer — the wrong one — and would silently produce a bad in-scope set rather than failing. Anyone pointing it at a 1-step zip must pass the PR layer explicitly.

Recommendation: keep G6 on the list for Route B alone, and treat nusel_extract.py as optional — worth running only if we specifically want numbers directly comparable to Xin's nusel-table.tsv, which is a provenance argument rather than a physics one.

8. Route A adopted (2026-08-17)

Until now every full-chain run used a scratch copy of the entry config; the repo still carried the 8-name pipeline. That is no longer true — sbnd/wcls-img-clus-matching-xin.jsonnet now carries the full 15-stage production pipeline_names, matching sbnd_xin's run_pr_chain_batch.sh exactly, including protect_bundle + steiner_refresh (SBND production default since 2026-08-02).

Verified from the repo config, no scratch: rc=0, tracking-pr.root 211 KB, mabc.zip 3.8 MB, zero DL-vertex failures, merged particle tree reading reco nu 107.5 MeV numu -1.715 nue -15.000, 21.43 s/event.

Route A now runs without the reference arm it was meant to be checked against. The original plan was Route B first, then A validated against it. G6 is deferred (§7), which defers Route B with it. Route A is validated only in the sense that it runs, produces every expected artifact, and reproduces T_tagger/T_kine values across configuration changes — not in the sense that it has been shown to agree with the 2-step. That comparison remains the outstanding piece of work.

Cost

15.0 s → 21.4 s/event, +43%, driven almost entirely by the DL vertex (§7.2: 29 ms → 6.5 s). Scaling the issue-11 run naively: 13,217 events went 13h39m / 261.5 core-hours at 8 stages, so 15 stages projects to ~374 core-hours, ~19 h wall at 20 cores. Treat that as an order-of-magnitude figure — it extrapolates a single cosmic-dominated event, which is exactly what G7 exists to replace.

The silent-failure checker

Making the full chain the default promotes one hazard to production-critical: if setup-dlvtx.sh is not sourced, every event falls back to the geometric vertex, logs one WARN, and still exits 0. A whole campaign could be computed the wrong way and look fine.

New: sbnd/check-pr-run.sh <lar.log>…, which exits non-zero if any known silent mode fired — DL fallback, an RSE attacher missing from the fcl inputers, rse_from_metadata falling back, the labeler passing an event through unlabeled, BLOB LOSS in a split, or tracking_visitor running with no ROOT file to show for it. Every entry corresponds to a bug this chain has actually shipped; the recurring shape is plausible output with wrong provenance, starting with the sp.jsonnet extVar that silently selected the wrong ROI thresholds. Tested both ways: OK on the Route A run, FAIL with the right diagnosis on the no-torch control.

Any bulk harness should call it per event. A run that is not audited is not validated.

9. The two routes, for the record

Route A — extend the 1-step in place

Add the 5 (or 7, with protect_bundle+steiner_refresh) names to pipeline_names in wcls-img-clus-matching-xin.jsonnet:

pipeline_names=[
  'switch_scope','unmerge_bundle','unmerge_assoc',
  'steiner','fiducialutils',
  'tagger_check_tgm','tagger_check_stm','tagger_check_fc',
  'protect_bundle','steiner_refresh',
  'tagger_check_neutrino',
  'numu_bdt_scorer','nue_bdt_scorer',
  'tracking_visitor','tagger_output',
]

Pros: one edit; labeler truth and PR verdicts on the identical tree; no extra I/O; harness unchanged apart from keeping new outputs.
Cons: hits G1, G2, G3, G4 immediately; no per-event TLA knobs, so all ~60 SBND_* switches become compile-time choices in our entry config.

Route B — write a pctree, run the 2-step PR job on it

Persist a post-Q/L pctree (G6 — a small pass-through tap, not the one-line tensor_outname an earlier draft claimed), then run the canonical toolkit cfg/pgrapher/experiment/sbnd/wct-pr-perevt.jsonnet per event — the same file Xin's driver runs.

Pros: bit-comparable with Xin's chain by construction; per-event TLAs work, so real run/subrun/event reach Trun (G3 dissolves); nusel_extract.py and pr_scores_table.py work unmodified.
Cons: a second process and a ~pctree-sized file per event; the truth labels and the PR verdicts live in different files.

Recommendation. Do B first as the reference, then A and check A against B. B is nearly free (one jsonnet argument plus a second wire-cell call, and its jsonnet is already in our tree), it side-steps G3 and G4 entirely, and it gives us the ground truth to validate A against. Then A is what we actually run at scale, once it reproduces B. This is the same 1-step ≡ 2-step equivalence argument that already worked for the clustering+matching half.

Suggested sequence

  1. Unblock G1 (nue XGBoost weights) and G5 (pr_display) — both done 2026-08-17.
  2. Decide G2 — done 2026-08-17: the uBooNE scn UPS product supplies torch+sparseconvnet, wired by setup-dlvtx.sh (§7.2). Remaining decision is whether the +6.8 s/event is worth it, which needs a multi-event measurement.
  3. G6 — deferred by owner decision 2026-08-17: it buys only Route B, so it is done when we take Route B up, not before. Needs a pass-through tap component (§7), not a config argument.
  4. Route B pilot, 10 events — wct-pr-perevt.jsonnet with the full 15-name pipeline. Measures G7. Produces tracking-pr.root + mabc-pr.zip + nusel-evt*.tsv with correct RSE.
  5. Route A pilot, same 10 events — compare T_tagger leaf-by-leaf and the mabc-pr.zip layers against step 4. Any difference is a real 1-step/2-step divergence, not noise.
  6. Fix G4 — add bee_sink to clus_pr so PR Bee layers share mabc.zip and the event index stays aligned.
  7. Split the labeler in two — done 2026-08-17 (§6.7, verified §6.8): truth is now attached upstream of the PR node and is independent of every PR knob.
  8. Fix G3 via the labeler's metadata — with instance A upstream, the PR node's input tensor set already carries the true RSE; add rse_from_metadata to MABC and the two ROOT visitors. Not rse_from_ident, which yields run/subrun = 0.
  9. Scale, once 4≡5 and the per-event cost is known.
