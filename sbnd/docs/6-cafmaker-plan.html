Wire-Cell CAFMaker — plan

Getting SBND Wire-Cell reconstruction into the Common Analysis Format, as larwirecell/CAFMaker. A plan to argue with, not a design to build yet.

Work dir /exp/sbnd/data/users/yuhw/production-prep/cafmaker-dev · follows on from the PR-chain port (ai-helper #13) · 2026-08-18

The two answers up front. Q1 — can everything in tracking-pr.root go into CAF? Mechanically almost all of it can, but two of its seven trees should not, and ~97% of the flagship tree is BDT input features rather than reconstruction output. Recommended: a tiered block, core always, BDT internals behind a flag. Q2 — is there anything CAF needs that I can't fill? Yes, five things — and the most important is that tracking-pr.root contains no truth or truth-matching whatsoever, which CAF requires for any MC analysis. That information exists, but in a different output stream.

There is also a design question that outranks both: CAFMaker should almost certainly not read tracking-pr.root at all. See §7.

1. How sbncode/CAFMaker works

The reference implementation is an art producer plus a set of free-function fillers.

The filler convention is uniform and worth copying verbatim:

void Fill<Component>(const <InputType>& input,
                     [auxiliary data, config],
                     caf::SR<Type>& out,
                     bool allowEmpty = false);

Const inputs, one non-const SR* output, modified in place. Fillers are free functions, not classes, so they compose and test independently of art. CAFMaker links sbnanaobj::StandardRecord and sbnanaobj::StandardRecordFlat — the data model lives in a separate repository from the maker, which matters for §7.

2. The CAF data model, and where a second reconstruction goes

caf::StandardRecord is one entry per spill. Its reco content is slice-centric: std::vector<SRSlice> slc, one per Pandora slice, each carrying vertex, truth, tmatch, fmatch, nu_score, crumbs_result, nuid, and a SRSliceRecoBranch of tracks and showers.

The important precedent: SRInteractionDLP. Sitting at top level in StandardRecord — beside slc, not inside it — are std::vector<SRInteractionDLP> dlp and dlp_true. That is the ML/SPINE reconstruction: a second, independent reconstruction of the same event, with its own interaction→particle hierarchy rather than Pandora's slice→PFP one. Its 47 members (vertex, is_contained, is_fiducial, is_cathode_crosser, flash_*, match_ids, particles, topology) mirror duneanaobj's SRInteraction/SRRecoParticle model.

This is the shape Wire-Cell should take. WC has no slice concept, and forcing it into SRSlice would misrepresent it. It does have exactly one main vertex per candidate and a particle-flow tree hanging off it — which is what SRInteraction is.

One thing that looked promising and is not. SRNuID is described as "neutrino ID features for BDT inputs", which sounds like a home for T_tagger. It is 10 variables — Pandora's NeutrinoID features (nufspfos, nutothits, nuvtxy, …). It is not a general BDT-input container, and T_tagger's 1216 have no home there.

The DLP block is present but empty — ndlp = 0 in every event. 433 rec.dlp* branches exist in the schema and cost real space in the file, but SBND production does not run the ML reconstruction that fills them. So SRInteractionDLP is a schema precedent, not a working example: it proves the "second reconstruction at top level" slot is legitimate and already carried, but nobody has exercised that path in SBND, so there is no operational pattern to copy — and no contention if Wire-Cell takes an adjacent slot.
This forces a correction to §5.2 as first drafted. I argued the ~1174 BDT-input branches were a size problem. Against a measured 631 kB/event, 1023 floats is ~4.1 kB — about 0.65%. Size is a weak argument and I should not have led with it.

What survives, and is stronger:
  • Branch count. The flat CAF has 2662 branches; adding ~1200 is a +45% increase in schema width. Flat-CAF tooling, dictionaries and review all scale with branch count, not bytes.
  • Meaning. They are one selection's intermediate features, uncharacterised on SBND, shipped to every analyser.
  • Review burden. Every branch is a permanent commitment in a shared schema.
The tiering recommendation stands; the justification changes.

4. What Wire-Cell actually produces

4.1 Where to find one

tracking-pr.root is written into the job's current working directory, under that fixed name — there is no path or run/subrun/event in it (PR-chain doc §7.1). In the 1-step chain that means one file per per-event working directory, e.g. the issue-11 harness layout:

<outdir>/work/e_<fileidx>_<evtidx>/tracking-pr.root      # 1-step, one event per lar process
<out_root>/pr_evt<ID>/tracking-pr.root                    # sbnd_xin 2-step, run_pr_chain_batch.sh

Because the harness deletes its per-event working directory after moving the Bee zip out, no durable copy existed anywhere on disk. A reference set has been preserved for this project, renamed by RSE (which the file itself cannot tell you):

All ten events of MCP2025C v10_14_02 run 925-23 (the first file of prabhjot/…/cluster_evaluation/mc_paths-100files.lst), produced by the current build with the full 15-stage pipeline. 1.2 MB total.

Those sizes are not noise — they are the two states of this file, and they matter for CAFMaker. The 8 kB files contain only T_bad_ch, T_proj and Trun: T_tagger, T_kine, T_rec_charge and T_proj_data are entirely absent. That is every event where the neutrino tagger selected no candidate — 6 of these 10. So "no PR content at all" is the common case, not the exception, and a filler must treat absent trees as normal rather than as an error.

Worse, that signature is indistinguishable from the multi-event corruption of G9. The corrupted lar -n 5 file measured 8261 bytes with T_tagger/T_kine absent; a legitimate no-candidate event here measures 8243–8282 bytes with exactly the same three trees. You cannot tell a silently corrupted production run from a run where the tagger declined every event by inspecting the files. That is a strong additional argument for §7: read the products in memory, where "no candidate" is an explicit state rather than an absent tree.

The find that changes the answer: T_rec_charge carries particle_id. I expected per-particle geometry to be missing — it is not, it is just not pre-aggregated. 5. Q1 — can all of tracking-pr.root go into CAF?

Mechanically, most of it. In practice, no — and you would not want it to. Three separate reasons, in decreasing order of importance.

4.1 Two trees are display data, not reconstruction

T_proj_data (per-channel projections) and T_bad_ch (dead-channel ranges) exist to drive the Magnify viewer. Per-channel waveform-adjacent content is precisely what CAF is designed not to carry, and dead channels are detector state, not per-event reco. These belong in Bee/Magnify and should stay there.

4.2 ~97% of T_tagger is BDT input, not output

42 of 1216 branches are *_score — numu_score, nue_score, cosmict_score plus 39 sub-BDT scores. The other ~1174 are the features those BDTs consume (br3_5_v_shower_main_length, tro_4_v_medium_dQ_dx, …). They are intermediate quantities of one particular selection, not a description of the event.

Two consequences. Size: 1023 floats ≈ 4.1 KB per interaction before the 190 vector branches — CAF is meant to be the small, widely-copied format. Meaning: these features encode uBooNE's selection logic. Shipping them to every analyser invites use of variables whose SBND behaviour nobody has characterised.

And the scores themselves are uncalibrated on SBND. Both BDT weight sets are the stock uBooNE-trained XMLs, unretrained (PR-chain doc §3.3, doc pr/2 gap G1). They are usable for availability and relative ranking, not as probabilities. Whatever lands in CAF must be named and documented so that is unmissable.

6. Q2 — what does CAF need that I cannot fill?

Five gaps. The first is the one that matters.

What CAF wantsStatusWhere it actually is
1truth, tmatch — SRTrueInteraction / SRTruthMatch, and per-particle match_ids / match_overlaps absent Verified: tracking-pr.root has zero truth or matching branches. WC's truth lives in a different stream — the labeler's per-blob trackid, its truth_per_track tensor and nugraph.h5. Every MC analysis needs this, so it has to be plumbed. This is the single largest piece of work.
2fmatch / opt0 — flash match and t0 absent here Exists as cluster_t0 / matched_flash_gid / lm_flag on the pctree cluster scalars, written by QLMatching. Not in this file.
3containment / cosmic verdicts, per interaction absent here TGM / STM / FC / LM are per-cluster flags in the Bee tagger_* layers and the log. The cosmict_* family in T_tagger is uBooNE's cosmic BDT — a different thing; do not substitute it.
4PID richness — pid_scores[6], chi2_per_pid[6], csda_ke, mcs_ke, primary_scores[2] not computed WC assigns one PDG and one KE per particle. There is no per-hypothesis likelihood to fill. Leave the arrays empty rather than fabricate them.
5bookkeeping — size (voxels), fragment_ids, ppn_ids, module_ids, uncertainties no analogue cluster_id / real_cluster_id / sub_cluster_id are the nearest equivalents and are worth carrying under WC names. WC reports per-point chi2/ndf, not propagated errors.

A structural mismatch worth naming. SRSlice presumes Pandora slices; Wire-Cell has no slice. It has clusters, flash bundles, and one selected main vertex. Any attempt to populate slc would either invent a slice per WC cluster or claim one slice per event — both misleading. This is the strongest argument for the interaction model in §7.

7. Proposed design

Decision that outranks the two questions: do not read tracking-pr.root. It is a Magnify/debug artifact, and it is not multi-event safe — both writers share one filename (RECREATE + UPDATE), so lar -n N silently produces an 8 KB file with T_tagger and T_kine absent (PR-chain doc G9). CAF production runs many events per process, so a file-parsing CAFMaker would be building on the one output that provably breaks under exactly that workload.

Instead, CAFMaker should take the same TaggerInfo / KineInfo / TrackFitting / PR-graph objects in memory that UbooneTaggerOutputVisitor and SbndPrMagnifyTrackingVisitor already read — i.e. a sibling visitor, not a downstream parser. tracking-pr.root then stays what it should be: a debug dump.

7.1 Where the data model should live

(a) Reuse SRInteractionDLP

Zero new sbnanaobj work. But the fields are SPINE-shaped: many unfillable (ppn_ids, size in voxels, softmax scores), and reusing a field whose meaning differs is worse than leaving it out.

Good as a two-week prototype, bad as the destination.

(b) New SRWireCell{Interaction,Particle}

Clean semantics, WC-native names, room for the tagger verdicts and the score tiers. Costs an sbnanaobj PR and SBN-wide review — the data model is a separate repo with its own review culture.

Recommended destination.

Suggested route: prototype against (a) to prove the fillers and the numbers, then propose (b) upstream with real output in hand. That converts an abstract schema discussion into a review of something that already works.

Mirroring sbncode/CAFMaker's free-function filler convention exactly, so the code reads familiarly to anyone who knows that package.

7.3 Phasing

  1. Verify the particle-id join. Confirm T_kine's particle ordering and T_rec_charge's particle_id agree. Everything downstream depends on it.
  2. Interaction level only — vertex, Enu, 3 headline scores, verdicts. Smallest end-to-end slice that produces a readable CAF.
  3. Particles — PDG, KE, geometry aggregated per particle_id.
  4. Truth (gap 1) — the big one; needs the labeler stream, not this file.
  5. Score tiers + flash/verdict plumbing (gaps 2 and 3).
  6. Propose the schema upstream (7.1b).

8. Open questions for you

  1. Who consumes this CAF? If it is SBN-wide analysis, the schema must go through sbnanaobj review and 7.1b is mandatory. If it is our own studies for now, a private block is far faster. This changes the whole shape of the work.
  2. Does WC output need to sit alongside Pandora in the same CAF file (so analysers can compare per event), or is a separate WC-only CAF acceptable? The former is much more useful and much more intrusive.
  3. Is truth in scope now? It is the largest single piece and the only one requiring a second input stream. Deferring it gives a data-only CAF much sooner.
  4. Do the BDT scores belong in CAF at all, given they are uBooNE-trained and uncalibrated for SBND? Defensible either way, but it should be a decision rather than a default.
  5. Which reco is authoritative for the vertex when WC and Pandora disagree? Not our call to make silently.
