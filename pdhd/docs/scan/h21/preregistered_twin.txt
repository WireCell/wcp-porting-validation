**The gate this file is:** each arm must move *these named items and no others*. The PDVD

## What is predicted, and on what arithmetic

* `shape_flat` fires when `ks_mu + ks_margin >= ks_flat` (`CheckSTM_Michel.cxx:2904`).
  The offline formula reproduces production's own `shape_flat` bit on **86/86** misses and
  **109/110** hand-THRU. The single disagreement is `028084_17/38`, whose reject is
  `profile_sparse` with `ks_mu = ks_flat = 0` — the KS test never ran on it. It is therefore a
  degenerate row, not a counterexample, and it is excluded from the sweep by the
  `bits == {shape_flat}` condition anyway.
* P1 (`topology_stop_evidence`) clears the *shape* bits, so only candidates whose whole reject
  set is clearable can move. Eligibility is `bits ⊆ {shape_flat, no_bragg}`, plus
  `profile_sparse` when `topology_clears_sparse` is on. An item carrying `plateau_off_mip`,
  `stop_near_boundary`, `stop_unmatched` or `not_muon_pid` cannot move and is excluded.
* All 26 `shape_flat`-only misses carry `has_pass = 1` and `in_fv = 1`, so no other gate blocks
  them.

## Overlap, stated in advance

`ks_margin` and P1 are **not** additive. Four items appear in both h21k and h21a
(`028084_18/108`, `028084_19/59`, `029107_20/57`, `029107_4/69`), so a combined arm is predicted
to gain **fewer** than 11 + 13. The combined arm is deliberately left to wave 2, after each
mechanism is attributed on its own.

## What would falsify the whole approach

If an arm moves items absent from its list, the offline model of the reject logic is wrong and
every sizing number in this campaign — including the ones that argued *against* the plateau
window — must be recomputed before anything is flipped. That is the point of naming items rather
than quoting counts.

## Explicitly NOT predicted

* Downstream effects: a candidate whose `is_stm` flips may claim clusters or pieces differently,
  which can perturb *other* candidates. The branch census (`d51g_branch_census.py --pts`) is the
  instrument for that, and any such movement is a finding, not a failure.
* `michel_found` movements. P1 reads the Michel object but does not create one; if
  `michel_found` moves anywhere, that is unpredicted and reportable.
