## 1. The two axes, measured

The ctpc is an exact 2-D lattice whose two cell edges come from **different
detector quantities**:

```
PointTreeBuilding.cxx:312   x = time2drift(face, time_offset, drift_speed, slice->start())
PointTreeBuilding.cxx:313   y = pitch_mags[apa][face][plane] * (wind + 0.5) + proj_centers[...]
```

so the x edge is `nticks_live_slice · tick · drift_speed` and the y edge is the
wire pitch. They are unrelated numbers that happen to be close on some
detectors.

| detector | drift step | pitch U / V / W | pitch / drift | source |
|---|---|---|---|---|
| SBND | 3.126 mm | 3.000 / 3.000 / 3.000 | **0.96** | **measured** — `pr_evt100135/222/322` |
| PDVD | 2.9615 mm | 7.650 / 7.650 / 5.100 | **2.58 / 2.58 / 1.72** | **measured** — `evt298595` |
| PDHD | 3.152 mm | 4.666 / 4.669 / 4.800 | 1.48 / 1.48 / 1.52 | *derived* — `pdhd/params.jsonnet:122` (1.576 mm/µs) × `pdhd/clus.jsonnet:78,82` (4 × 0.5 µs) |
| uBooNE | 2.202 mm | 3.000 | *1.36* | *derived* — `qlport/uboone-mabc.jsonnet:148-151` (1.101 mm/µs, `tick: 0.5 µs`, `nticks_live_slice: 4`) |

Two corrections to the framing this round started from, recorded rather than
glossed:

- **uBooNE's 3.2 mm is the WCP prototype constant**, not the toolkit's. The
  prototype used `unit_dis = 1.6 mm/µs`; the live toolkit chain configures
  1.101 mm/µs, giving a **2.202 mm** slice. That makes uBooNE *more*
  anisotropic than SBND (1.36 against 0.96), not equally isotropic. It changes
  nothing about the recommendation — uBooNE is a frozen reference and the knob
  stays off there — but it does change the "which detectors are exposed"
  table, and it is the same shape of error as doc 32 round 2's PDHD
  correction: an exposure table built from arithmetic rather than measurement.
- **PDVD's production drift speed is 1.48073 mm/µs, not the 1.568 jsonnet
  default** (`protodunevd/params.jsonnet:131` against the runner TLA recorded
  in `pdvd_track_fitting.json:3`). The measured 2.9615 mm confirms the
  production value is what the arms actually ran with; at the jsonnet default
  the step would be 3.136 mm and the ratios would be ~5 % smaller.

Every distance taken in this cloud today is plain isotropic Euclidean in mm.

## 2. Why SBND never saw this and PDVD cannot avoid it

A radius `r` in an isotropic metric buys `r/pitch` pitches of tolerance and
`r/dx` drift steps of tolerance. When `pitch ≈ dx` those are the same number
and the metric is, by accident, correctly normalised. That is SBND (0.96) and
it is why a decade of tuning against SBND- and uBooNE-shaped detectors never
produced a reason to look.

On PDVD U/V the same radius buys 2.58× fewer pitches than drift steps. The
0.2 cm the PR chain passes is 0.675 of a drift step but only **0.261 of a
pitch** — and since the lattice is exact, a tolerance below half a pitch
**cannot be satisfied for a whole band of phases whatever the charge**. That is
doc 32's confirmed finding; this document is the other half of the sentence
doc 32 §15 ended on ("write it as a fraction of the pitch **and of the drift
step**").

## 3. Four 2-D families — and only one of them is a lattice

| family | tree | quantised? | metric surface | cuts in use |
|---|---|---|---|---|
| **1. ctpc** | `Grouping::kd2d`, scope `ctpc_a%df%dp%s` on `{"x","y"}`, `Facade_Grouping.cxx:500-534` | **yes — exact (drift-step × pitch) lattice** | **exactly two functions**: `get_closest_points` `:680`, `has_closest_point` `:693` | 0.2 / 0.3 / 0.6 / 1.0 / 1.2 cm |
| 2. `Cluster::kd2d` | scope `"3d"`, `2dp{p}_x/_y`, `Facade_Cluster.cxx:693-722` | no — continuous projection | `get_closest_2d_index` `:726` | 0.5, 2.1 cm |
| 3. `DynamicPointCloud::kd2d` | own `nfkd_t(2)` per (plane, face, apa), `DynamicPointCloud.cxx:74-83` | no | `:288`, `:341`, `:403` | 7.5, 2.4, 1.8, 1.2, 0.6, 0.3 cm |
| 4. `Multi2DPointCloud` | own `nfkd_t` per plane, `Facade_Util.cxx:245-310` | no | `:271`, `:283`, `:296` | 1.5, 2.4, 10 cm |

All four use the identical projection `y = cos(angle)·z − sin(angle)·y` and all
four are isotropic squared-L2 in mm. **Only family 1 carries the exact lattice
argument.** Families 2–4 are continuous projections of 3-D points, so a
sub-pitch distance there is *attainable*; the case for normalising them is a
weaker resolution argument, not a geometric impossibility, and this document
does not make it. Keeping that line sharp is what separates a recommendation
from a hunch — see §9.

Two structural facts shrink family 1 to something small enough to change
safely.

**The entire ctpc metric surface is two functions**, sharing one projection
block:

```cpp
// Facade_Grouping.cxx:680-707
double x = point[0];
const double angle = fastgeom(apa, face).angle[pind];
double y = cos(angle) * point[2] - sin(angle) * point[1];
const std::array<double, 2> query{x, y};
return skd.radius<std::array<double,2>>(radius * radius, query);   // get_closest_points
return skd.exists_within(radius * radius, query);                  // has_closest_point
```

Everything else on `Grouping` that touches the ctpc works in **integer
`(slice_index, wind)` space** and forms no Euclidean distance at all —
`get_closest_dead_chs` `:709`, `in_dead_gap` `:726`, `get_overlap_dead_chs`
`:813`, `get_overlap_good_ch_charge` `:900`, `is_blob_plane_bad` `:1150`,
`convert_3Dpoint_time_ch` `:772`. The **dead** half of `is_good_point` is
therefore already pitch-relative (`ch_range` counts wires); only the **live**
half is blind. One function has measured one thing in wires and the other in
centimetres since it was written.

**The scale factor is already in hand — nothing needs plumbing.**
`fastgeom_t` (`Facade_Grouping.h:106-124`) caches `angle, pitch, center,
time_offset, drift_speed, tick, iface` per (apa, face), and
`cache().map_nticks_per_slice` is filled in the *same* `fill_dv_cache` loop
(`Facade_Grouping.cxx:456`) as `map_tick` and `map_drift_speed`, keyed the same
way. So the per-(apa, face) drift step is `nticks_per_slice · tick ·
drift_speed` — one line beside the three already at `:764-766`. No new config
key, no new metadata, no new argument to thread through 20 call sites.

## 5. The geometry: why one number works everywhere

Define the anisotropic metric to scale **only** the pitch axis, so a radius
keeps its exact drift-axis meaning:

```
s = min(1, drift_step / pitch)          per (apa, face, plane)
d² = Δx² + (s · Δy)²
```

Covering every lattice phase in the worst case — a query point at the far
corner of a cell — needs

```
isotropic     r ≥ sqrt((dx/2)² + (pitch/2)²)
anisotropic   r ≥ sqrt((dx/2)² + (s·pitch/2)²) = dx/√2
```

because with `s = dx/pitch` **both terms collapse to `dx/2`**. The anisotropic
requirement is a property of the drift step alone — the same number on every
plane of a detector, and nearly the same number on every detector:

| | SBND | uBooNE | PDHD | PDVD W | PDVD U/V |
|---|---|---|---|---|---|
| isotropic r needed | 2.166 mm | 1.861 mm | 2.871 mm | 2.949 mm | **4.102 mm** |
| anisotropic r needed | 2.166 mm | 1.557 mm | 2.229 mm | 2.094 mm | **2.094 mm** |

The isotropic requirement spans 1.86 → 4.10 mm, a 2.2× spread; PDVD U/V's
4.10 mm is 0.536 of a pitch, **above the 0.392 threshold at which doc 32 §19.4
measured W unpinning and a 45 cm unsupported tail appearing**. That is the bind:
isotropically, full coverage on U/V is not purchasable at any price PDVD can
pay. The anisotropic requirement spans 1.56 → 2.23 mm and the legacy 0.2 cm is
already within 10 % of it everywhere.

Equivalently, and this is the cleanest way to state the knob: under this metric
the pitch tolerance in units of a pitch is **`r/dx` — one number for all
three planes of a detector** (0.675 on PDVD at r = 0.2 cm; 0.640 on SBND, since
`r/dx` still follows each detector's own drift step), where isotropically it is
`r/pitch` and varies 0.26 → 0.39 across PDVD's three planes alone. **`r/dx` is
the single scale-free tuning parameter**, and it is scale-free in the sense
that matters: it no longer depends on which plane you ask.

The clamp at `s ≤ 1` is deliberate: the metric may only ever *relax* a plane
coarser than the drift step, never *tighten* one that is finer. SBND's raw
`dx/pitch` is 1.042, so it clamps to exactly 1.0 and the metric becomes the
identity — **SBND is unchanged structurally, not by configuration**. That is
the "keep the two separate paths" requirement satisfied by construction rather
than by remembering to leave a knob off.

## 6. The measurement

Interior trajectory points only: the first and last 3 points of each polyline
are dropped, because those are exactly the points `examine_end_ps_vec`'s pop
loop accepted, and including them measures survivorship instead of geometry
(doc 32 §10). PDVD n = 6703 (19 `stm_fit` polylines + 4 calib segments), SBND
n = 729 / 887 / 242 (calib segments; these arms carry no `stm_fit` layer).

The **ceiling** column is doc 32's `lattice_model` — the fraction of a cell
covered when *every* neighbouring cell is occupied, i.e. the best any event can
give. Comparing measured against ceiling is what separates "limited by the
lattice" from "limited by the charge".

**PDVD 039252/2 evt 298595:**

| arm | all-3 | U | V | W | ceiling U / V / W | drift reach |
|---|---|---|---|---|---|---|
| isotropic r = 0.2 cm (legacy) | 0.175 | 0.436 | 0.428 | 0.624 | 0.470 / 0.470 / 0.705 | 2.00 mm |
| isotropic frac 0.35 — **shipped** | 0.287 | 0.564 | 0.573 | 0.624 | 0.662 / 0.662 / 0.705 | 2.68 mm |
| isotropic frac 0.50 — grew the tail | 0.651 | 0.765 | 0.807 | 0.770 | 0.974 / 0.974 / 0.941 | 3.83 mm |
| **anisotropic r = 0.2 cm** | **0.703** | 0.776 | 0.818 | 0.809 | 0.996 / 0.996 / 0.996 | **2.00 mm** |

**SBND control, three arms:**

| arm | 100135 all-3 | 100222 | 100322 |
|---|---|---|---|
| isotropic r = 0.2 cm | 0.833 | 0.612 | 0.752 |
| isotropic frac 0.35 | 0.833 | 0.612 | 0.752 |
| isotropic frac 0.50 | 0.833 | 0.612 | 0.752 |
| anisotropic r = 0.2 cm | 0.833 | 0.612 | 0.752 |

Four readings:

1. **At the unchanged legacy radius the anisotropic metric beats the isotropic
   frac 0.50 that was rejected for growing a 45 cm tail — 0.703 against 0.651
   — while reaching 2.00 mm in drift instead of 3.83 mm.** It dominates the
   shipped 0.35 on every plane. There is no isotropic value that reaches this
   coverage at this drift reach; that is §5's arithmetic showing up in data.
2. **PDVD stops being lattice-limited.** Under the legacy metric the measured
   rates are 93 % / 91 % / 89 % of their ceilings — PDVD is pressed against the
   geometry, exactly doc 32's finding. Under the anisotropic metric they are
   78 % / 82 % / 81 % of a ceiling that is now 0.996 on all three planes. The
   binding constraint moves from the lattice to the charge, which is where
   SBND has always been: SBND's own isotropic rates are 78–94 % of its 0.988
   ceiling. **The metric puts PDVD in SBND's regime.**
3. **The SBND control is exact, not approximate.** All four arms are identical
   to the digit under all four metrics, because `s` clamps to 1.0 and the
   scaled tree *is* the original tree. This is a structural identity, so it
   will survive any event sample.
4. **The two-round cost is modest.** The circumscribing-circle query
   enumerates 5.10 ctpc points per (point, plane); the ellipse accepts 2.20 —
   a 2.31× inflation on small absolute counts.

## 7. The design — three options, one recommendation

### Recommended: scale at query time, exact, inside the two functions

`get_closest_points` returns **all** candidates within the radius
(`NFKDVec.h:343`; the argument is r², results are unsorted, comparison is
strict `<`), so circumscribing the ellipse and re-filtering by the true metric
is **exact**. Two cheap brackets keep the common cases allocation-free:

- `exists_within(r_in²)` true ⇒ **accept** — the inscribed circle is contained
  in the ellipse;
- else `exists_within(r_out²)` false ⇒ **reject** — the ellipse is contained in
  the circumscribed circle;
- else `radius(r_out²)` + a per-candidate ellipse test — the only allocating
  path, and the only one that loses `exists_within`'s early termination.

Both brackets are exact, so no correctness rests on them; they are pure
optimisation and can be dropped if measurement says they do not pay.

> **Trap to carry into the code.** `has_closest_point` is built on
> `exists_within`, which returns a **boolean**, not the nearest point. A
> two-round filter written on top of a *nearest-only* query would be silently
> wrong: the Euclidean-nearest point can lie outside the ellipse while a
> Euclidean-farther point lies inside it. Only `get_closest_points` may be
> filtered.

Blast radius: two functions in one file, plus one line in `fastgeom()`.

### Rejected: scale the stored `y` at ctpc build time

Cheapest per query and it preserves the fast path exactly, but:

- **`Grouping::m_dv` is null while `add_ctpc` runs.**
  `PointTreeBuilding.cxx:567` calls `set_anodes` and never
  `set_detector_volumes`, so `fill_dv_cache` is a no-op there and the build
  code uses its own `get_tick`/`get_drift_speed` helpers. It never reads
  `nticks_live_slice` at all. Recoverable, but it means the scale must be
  reconstructed in a second place.
- Scaled units then leak into every ctpc consumer and, worse, into the
  **returned distances**, which callers `sqrt` into physical lengths
  (`Facade_Util.cxx:167-169`).
- The pctree dump changes — and our own offline scripts, including this one,
  read it.

### Rejected: a second scaled array plus a second scope

Keeps the fast path *and* leaves the original tree untouched, but
`NFKDVec::Tree` **owns** its coordinate columns (`NFKDVec.h:412`, filled by
`append()`; `ScopedView` does not use `bind_external`), so a second scope costs
a full second copy of every column plus a second nanoflann index per
(apa, face, plane). It also lands on a live hazard:

> `Scope::hash()` includes `name` but `Scope::operator==` does **not**
> (`util/src/PointTree.cxx:22-43`). Two scopes differing only in `name` are
> "equal" but hash differently — today they get separate trees by bucket luck,
> and on a hash collision the second silently aliases onto the first's tree
> with no error. Any new scope must be distinguished by its **coords names**,
> which `operator==` does compare — never by `name`.

### Knob shape

Default OFF, PDVD-only, following the two live `pitch_frac` chains exactly:
`TrackFitting::Parameters` via the runtime track-fitting JSON
(`TrackFitting.h:149`, `TrackFitting.cxx:62-67`, `:232`) and the
`NeutrinoPatternBase` member via jsonnet (`TaggerCheckNeutrino.cxx:463`,
`:1034`, `:2438`). Knob-off costs nothing: as with `pitch_frac`, a zero value
skips the `fastgeom` lookup entirely and the metric folds back to isotropic.

### Precedent — the codebase already agrees

`two_d_connectivity_bad` / `two_d_gap_kill`
(`connect_graph_relaxed_strict.cxx:920-1000`, designed at `Graphs.h:260-283`)
is already a true anisotropic neighbourhood: a Chebyshev box of `dw` wires ×
`ds` slice steps on the integer `(wind, slice_index)` grid, with the slice step
taken from each seed blob's *own* tick span rather than a fixed mm. It is gated
by `two_d_check` and appears in no `cfg/` file. Alongside it: `time_tick_cut =
20` in ticks (`TrackFitting.h:193`), `ch_range` in wires, and `point2wind`
(`Facade_Util.cxx:551`) — the one place `y` is divided by pitch, feeding integer
lookups and never a metric. The idea in this document is not new to the
codebase; it has simply never been applied to the ctpc distance.

## 8. Relation to `good_point_pitch_frac` — subsume, do not stack

`good_point_pitch_frac = 0.35` is **live in PDVD production**
(`pdvd_track_fitting.json:52`, shipped 2026-09-04). It is a per-plane floor on
an isotropic radius, `r = max(0.2 cm, frac · pitch)` — a one-axis fix applied
to a two-axis object. Raising `r` to reach across a pitch necessarily reaches
proportionally further in **drift** as well, and that is why the value could
not be raised past 0.39: above it, W unpins and the loosened trim stops masking
the endpoint-selection defect of doc 32 §2.2.

§6 shows the anisotropic metric dominating the floor at every value tested, at
a strictly smaller drift reach. **Two overlapping knobs governing one radius is
a trap**, so the recommendation is that the metric *retires* the floor rather
than stacking with it: `good_point_pitch_frac` returns to 0 and
`pdvd_track_fitting.json` carries the new knob instead.

**Doc 32's guard rail does not translate.** "Do not raise this above 0.39
without fixing endpoint selection first" is expressed in pitch-fraction units
of an isotropic radius. Under the new metric the corresponding quantity is
`r/dx`, and the pitch reach it buys is uniform across planes rather than
varying 0.26 → 0.39. The bound must be **re-derived by measurement in the new
units**, not carried over by analogy.

## 9. What is not established

- **The tail question, which is decisive.** Under the anisotropic metric W's
  pitch reach rises 0.392 → 0.675 of a pitch, so **W does unpin in pitch**.
  What stays pinned is the drift axis. Doc 32 §19.4 established that the 45 cm
  unsupported excursion appears when W unpins, but *not* whether the mechanism
  runs through the pitch axis or the drift axis. This cannot be settled
  offline — a fitted trajectory is needed, and a trajectory is fitted *to* the
  metric under test. It is the first thing an implementation round must
  measure, and it could refute the whole proposal.
- **One PDVD event.** n = 6703 interior points, but from a single event, the
  same one doc 32 used. The population behaviour is not measured.
- **PDHD and uBooNE are arithmetic, not measurement.** No pctree dump exists on
  disk for either. PDHD at 1.48 is genuinely exposed and would move if the knob
  were ever turned on there; nothing here measures it.
- **Families 2–4 are censused, not measured.** No claim is made that they need
  normalising. They are continuous projections, so their case is a resolution
  argument rather than a satisfiability wall, and it would need its own
  evidence.
- **The query cost is bounded, not measured in situ.** 2.31× candidate
  inflation is an offline count; what matters is wall time on the clustering
  hot path, where `exists_within`'s early exit and the `std::array` stack query
  were both deliberate perf work (doc 28).
- **Survivorship persists.** Interior points of a fitted trajectory were never
  subjected to the test that produced the trajectory, but the trajectory itself
  is fitted to charge, so every rate here remains an upper bound.

## 10. Gates an implementation round would owe

1. **Knob-off byte identity** via `abtest/hash_archive.py` member content
   (never a raw archive md5, M2) on `abtest/events.txt`, at the **clustering**
   stage as well as PR, for **PDVD and PDHD**. This is the gate already
   outstanding from doc 32 round 3b, and it becomes more load-bearing here: the
   change is inside `has_closest_point`/`get_closest_points`, which every
   detector's `connect_graph_*`, `clustering_protect_overclustering` and
   `TaggerCheckTGM` call on the hot path, and which no PR arm exercises.
2. **Freshness proof** before any A/B (M1), and the binary pinned for the
   duration of the arms (a peer shares this tree).
3. **Compiled-config proof** — the key absent when off, present exactly once
   when on. Note the track-fitting JSON is read at **runtime**
   (`pdvd_track_fitting.json:2`), so a byte-identical compiled jsonnet proves
   nothing about the fit; the config gate and the binary gate are different
   gates.
4. `./build/clus/wcdoctest-clus`, plus a default-OFF guard case beside the
   existing `good_point_pitch_frac` one in
   `clus/test/doctest_clus_knob_defaults.cxx`.
5. **A knob-on arm graded on doc 32's two axes** — coverage *and* support
   (distance to nearest reconstructed 3-D charge), read as a delta because the
   knob-off baseline is not zero — with `stm_endtrim_grade.py`, and **the 45 cm
   tail as the explicit pass/fail**. Coverage alone would reward the change for
   everything it keeps.
6. **A query-cost measurement**, since the filter path trades `exists_within`'s
   early termination for a heap allocation on a per-point-per-plane hot path.
7. If the floor is retired as §8 recommends, the arm must show the metric
   reproducing or beating `good_point_pitch_frac = 0.35` on the 120-event
   manifest doc 32 round 3b established — not only on evt 298595.

## 11. Gaps in the shipped doc-32 fix

Recorded here because this census found them, not because this round fixes
them:

- The `pitch_frac` floor reached **`is_good_point` only**. `is_good_point_wc`
  (`:564`), **both** `test_good_point` forms (`:592`, `:600`) and
  `get_ave_charge` / `get_ave_3d_charge` (`:628`, `:646`) still take a bare
  isotropic radius.
- `test_good_point` is on the **clustering** hot path via
  `connect_graph_relaxed.cxx:183` and
  `connect_graph_relaxed_strict.cxx:887, 1730`, at the 0.6 cm default. At
  0.6 cm, 2r/pitch is 1.57 even on PDVD U/V, so it is above the satisfiability
  wall — exposed to the anisotropy, but not blocked by it.
- `get_ave_charge`'s 0.3 cm default gives 2r/pitch = 0.78 on PDVD U/V, **below
  1.0**, so it is blocked the same way `is_good_point` was. Its consumers are
  `NeutrinoVertexFinder` (`:414`, `:469`, `:2610`, `:2614`) and
  `pr118_connector_walk` (`NeutrinoShowerClustering.cxx:2949`). Nothing in doc
  32 or this document measures the consequence.

The anisotropic metric, being inside the two shared query functions rather than
at the call sites, would cover all six entry points at once — which is a
further argument for putting the fix there rather than threading another
parameter through 25 callers.
